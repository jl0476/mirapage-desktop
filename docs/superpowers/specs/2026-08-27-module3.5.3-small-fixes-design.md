## 2. 各项设计

### A. 瀑布流陈旧尺寸守卫（任务 1）

**根因（三点叠加）**：

1. `MasonryView.vue` 以 `v-else-if="viewMode === 'masonry'"` 挂载、切目录**组件实例复用**，而组件持有的 `measuredMap`（`:67`）从未在切目录时重置；
2. `triggerDimensionPrefetch`（`:437-456`）await IPC 回包后不校验 descriptor/currentPath 是否已变就直接写入；
3. 后果不可自愈：尺寸预读对已测路径跳过（`useMasonryLayout.ts:456-459`）、`mergeMeasured` 拒绝覆盖（`:132`）——正确回包先到、陈旧回包后到时，错误比例永久驻留。

**症状**：兄弟漫画目录同名编号文件场景（001.jpg…），A 目录的宽高比串进 B 目录同名卡片，本次会话内不再纠正。触发条件=远程慢 header + 快速切目录。

**关键事实**：measuredMap 的键是 `entry.path`＝相对 `currentPath` 的相对路径（`MasonryView.vue:434-436` 注释明确），键本身就不跨目录唯一——所以**整体重置**是唯一正确语义，不是过滤。

**修法（稳定语义键而非对象引用）**：

**先说一个否决项**：最初方案直接比较 `descAtStart !== props.descriptor` 对象引用——被推翻。FileList 给未传 descriptor 的本地源用的是内联字面量兜底（`FileList.vue:407`）：`:descriptor="descriptor || { type: 'local', rootPath: rootPath || '' }"`，父组件每次重渲染都产出新引用。引用比较会把本地瀑布流的正常回包误判为陈旧，且新增的 measuredMap 清空会把这种引用不稳定从「仅重启浏览位置」升级为「丢尺寸且未必重新触发预读」。

最终设计：watcher 与回包守卫统一比较**稳定语义键**：

```ts
// 复用仓库现成辅助（src/lib/sourceDescriptor.ts:64），likes 状态表已在同款场景消费它
`${descriptorId(props.descriptor)}|${props.currentPath}`
```

- 切目录 watch 的侦听源改为此 key 字符串——本地源重渲染拿到新对象引用但 key 不变，measuredMap 不再被误清；
- `triggerDimensionPrefetch` 在 await 前捕获 `(keyAtStart)` 快照，回包后与当前 key 不一致才丢弃。同一 Local descriptor 重建对象后，已测量尺寸不被清空、在途回包照常提交。

选语义键而非单调序号的理由不变：同一目录内的并发批次（快速滚动触发两次预读窗口变化）用序号会把合法批次误杀造成重复拉取；内容正确的迟到回包按键身份放行不产生任何错误。

**附带偏差（有意为之）**：`defineExpose` 增加 `measuredMap`。理由：① 守卫行为无法从 DOM 观测，单测必须直读；② 未来 G 项（锚定补偿）本来就要在这条测量提交路径上工作，届时也需要这个观测点。

**顺手修正（同文件相邻区，任务 1 携带）**：`useMasonryLayout.ts:433-435` 注释声称「尺寸收敛期间的视觉跳动也被锚定恢复」，实际 resize anchor 只挂在 ResizeObserver 上，测量批次路径不经过它。注释改为如实描述（这也为 G 项未来立项留下准确的事实基线）。

**明确不在本次范围**：视口上方 item 高度变化的 scrollTop 补偿本身（G 项）；本任务只保证「错误数据不进来」，不改变测量到达时的正常渐进收敛表现。

### B. archiveOpenError 导航清空（任务 2）

**现状**：store 唯一挂账字段 `archiveOpenError`（`fileBrowser.ts:401`），写入点两处（openArchive catch `:593`、submitArchivePassword catch `:660`），清空点**仅一处**（openArchive 入口 `:535`）。navigate/setRoot/up/openDescriptorAt 经 `invalidatePendingArchiveOnNavigate`（`:520-528`）只推进 epoch 清 pending/opening/progress，**不碰 error**；exitArchive 走 `takeAndCancelPendingArchiveOpen`（`:499-514`）同样不碰。组件侧 `FileBrowser.vue:382-383` immediate watch 还会在重挂载时把旧 store 值重新镜像回来。

**症状**：常驻横幅不是 toast——损坏包报错后切任意目录横幅仍在，离开页面回来重现，只能手动点关或下次打开任意压缩包才消。

**澄清**：密码弹窗的 `archivePasswordError` 是组件局部 kind 状态随弹窗提交/取消必清，与此无关。

**修法（两处各一行）**：

- `invalidatePendingArchiveOnNavigate` 顶部无条件 `archiveOpenError.value = null`（必须在「无在途事务提前 return」之前——失败已落地的错误恰恰处于无 pending 状态）；
- `takeAndCancelPendingArchiveOpen` 内追加同名清空（覆盖 exitArchive 路径，它是该函数的共用通道）。

语义口径：导航 = 显式离开意图，上一目录的打开失败提示随之失效；页内刷新列表（refresh）不动横幅。

### C. Settings remote 开关/上限错误处理（任务 3）

**现状**：三个控件两缺一全——

- 预载开关（`Settings.vue:100-103`）先翻转 UI 再裸 await `setArchivePrefetchEnabled(v)`，无 catch：IPC reject = unhandled rejection + 开关假成功（UI 变了，DB/Prefetcher 未变）；
- 缓存上限（`:106-110`）钳位正确，但 `settings.update(...)` 同样裸奔（settings store 的 `update()` 无统一兜底），同病；
- 清空缓存按钮（`:112-129`）已有完整范式：confirm → try/catch `window.alert(String(e))` → finally 复位 busy。

**修法（按控件串行化 + 最新请求胜出）**：仅失败回滚不成立——连续两次改值时，较早请求可以在较晚请求成功后才失败，`prev` 回滚会覆盖新值，且后端两次 IPC 完成顺序无保证，最终 DB/runtime 不等于最后一次用户操作。二选一里选**串行化**（不禁用控件，打字/连点体验不受损）：

- 每个控件维护一条 `writeTail: Promise<void>` 写入链，新操作 `.then()` 排在链尾——后端写完成顺序 == 用户操作顺序，最终态恒等于最后一次选择；
- 失败回滚与 alert 带**抑制条件（revision 判定）**：每控件维护递增 `latestReqId`，请求发起时捕获自己的 id；仅当 `reqId === latestReqId` 才允许回滚+告警，被后续操作顶替的旧失败静默吞掉。第二轮审查修正：不能按「显示值==尝试值」判定——ABA 序列（4096→8192→4096）下首个失败请求的尝试值与显示值重新相等，等值判据会误判自己仍是最新而错误回滚到中间值并误告警；
- **初载 ready 门（第四轮审查修正）**：`loadRemoteSection()` 的 DB 回填与用户写入存在竞态——门未开时 confirmed 种子停在默认值（DB 实为 4096 却回滚到默认 2048），且迟到的回填可能覆盖已开始的本地写。两个写入函数入口先 `await remoteSectionReady`（一次性 Promise，回填完成与加载失败路径都放行；用量刷新等网络型后续不拖延放行）。选挂起门而非禁用控件：语义集中在写入协议一处、不动模板与 NumberRow/ToggleRow 组件、测试环境 mock 下门即时打开不影响既有用例。「回填先于任何写意图生效」由结构保证——过门者的意图必不被覆盖（回填已定格），未过门者尚未触碰任何状态，无需单独的「写意图已开始」标志位；
- **回滚目标是 confirmed 确认基准，不是乐观 prev（第三轮审查修正）**：每控件维护一个确认 ref，与显示 ref 同种子初始化、并在 `loadRemoteSection()` 的 DB 回填处同步；**仅当一次写入成功才推进**。乐观 prev 会吸收前序失败请求的翻转——反例 `2048→4096(#1败)→8192(#2败)`：#2 是最新且失败，其捕获的 prev₂=4096 是被污染值，回滚后 UI=4096 而后端仍 2048；confirmed 从未受失败影响，回滚它恒有 UI==后端。

preview 形态（以开关为例，上限同构；**完整模板含四件套全部要素**——门、链、revision、confirmed）：

```ts
// 就绪门（第四轮）：一次性 Promise，loadRemoteSection 的回填完成/失败路径放行；
// 声明在组件 setup 顶层，与两控件的 writeTail / latestReqId 平级。
let fireRemoteSectionReady!: () => void;
const remoteSectionReady = new Promise<void>((resolve) => { fireRemoteSectionReady = resolve; });
let prefetchWriteTail: Promise<void> = Promise.resolve();
let prefetchLatestReqId = 0;

async function setRemotePrefetch(v: boolean) {
  await remoteSectionReady;               // 初载回填先于本写意图生效
  const reqId = ++prefetchLatestReqId;
  remotePrefetchEnabled.value = v;
  const call = prefetchWriteTail.then(() => setArchivePrefetchEnabled(v));
  prefetchWriteTail = call.then(() => undefined, () => undefined);
  try {
    await call;
    remotePrefetchConfirmed.value = v;      // 成功才推进确认基准
  } catch (e) {
    if (reqId === prefetchLatestReqId) {    // 仅最新请求回滚，目标是 confirmed
      remotePrefetchEnabled.value = remotePrefetchConfirmed.value;
      window.alert(String(e));
    }
  }
}
```

不做全局 settings.update() 兜底改造（影响面大且超出本次范围）；不引入 busy 态禁用（串行化已给出最终一致性，禁用徒增交互损伤）。

### D. RAR ERAR_EOPEN 归类 Io（任务 4）

**现状**：`rar_backend.rs:209-211` 把 `ERAR_EOPEN` 与 BAD_DATA/BAD_ARCHIVE/UNKNOWN_FORMAT 一起归 `CorruptArchive`（用户看到「压缩包损坏」）；`:218-220` 的 EREAD/EWRITE/ECREATE/ECLOSE 归 `Io`。

**取证**（unrar_sys 0.5.8 vendored 源码口径）：EOPEN = `Arc.Open(ArcName, FMF_OPENSHARED)` 失败——容器文件**物理打不开**（不存在/权限拒绝/锁定），unrar 已用共享模式规避常规占用；加密头打不开 unrar 显式给 BAD_PASSWORD，且本仓库 callback typed error 优先于裸码（`:282-288`），密码场景不经 EOPEN——**动它无误报面**。EOPEN 是「打不开」不是「打开了但内容坏」，归 Io 语义准确。

**media:// 层零可见差异**：lib.rs:566-568 当前 `Archive(_) => 422`，Io 与 CorruptArchive 都映射 422（lib.rs:551-552 注释自认）。本次不改 HTTP 映射（那是独立议题），只纠分类——价值在未来接入细分错误时的语义正确性 + 用户日志里不再出现「损坏」误导。

**测试**：现仓无 `map_rar_code` 断言（已 grep 证实，改动无搬迁成本）；补一张**整表特征锁测试**防再次漂移。

### F. 远程 ready fresh stat 复用——F3 砍半版（任务 6）

**取证账单**（比原记录严重）：

| 场景 | 每次 media:// GET 远端往返 |
|---|---|
| 已物化 ready 命中 | **4 次 HEAD**：handler 先 `src.stat` 再 `src.read_file` 两次 service 调用（lib.rs:271/337）× 每次 resolve 内 identity stat（service.rs:460→materializer.rs:485）+ fresh 校验 stat（service.rs:469→materializer.rs:613）|
| 流式（catalog ready 未物化） | 2 次 HEAD（fresh 校验在 DAO 无行时 `:611` 提前 return） |

两次 stat 输入**完全相同**纯重复。WAN 高延迟下翻页前白吃约 2 个 RTT 纯延迟（100ms RTT ≈ 0.4s）。

**修法（砍半版，不加 TTL）**：

- `Materializer` 新增 `ready_path_if_fresh_with_stat(origin, rel, format, known_stat: Option<&FileStat>)`：`Some(stat)` 时内部二次 stat 消失，其余逻辑逐行不变（校验顺序保持：stale 判定→磁盘长度→touch）；`FileStat` 已 derive `Clone, Copy`，直传即可；
- 原公开 `ready_path_if_fresh` 保持签名不动，委托 `_with_stat(..., None)`——`materializer.rs:1198-1201` 的 Materialize trait 桥接与其余四个调用点零改动；
**接线事实（比表面更深的约束）**：service 持有的是 `Arc<dyn Materialize>` **trait 对象**（service.rs:272），`ready_path_if_fresh` 与 `stat_origin` 都是 trait 方法、带「不支持」默认实现，Materializer 在 `impl Materialize for Materializer`（materializer.rs:1198）覆盖。因此接入是**四点改动**而非换一处调用名：

1. trait（archive_impl.rs）新增 `ready_path_if_fresh_with_stat(..., known_stat: Option<&FileStat>)`，默认实现直接退化为调 `ready_path_if_fresh`——其他物化 mock 实现零适配；
2. Materializer 新增同名 inherent 方法承载真正逻辑，原公开 `ready_path_if_fresh` 委托 `_with_stat(None)`；
3. `impl Materialize for Materializer` 覆盖新 trait 方法转发 inherent 版本；
4. service.rs resolve 分支（`:467-471`）切换为 `_with_stat(origin_desc, rel, *format, Some(&stat))`——resolve 已持有同一 URL 的 identity stat，直接喂下去。

**接线锁测试（验收本体）**：只测 materializer 单元层证明不了 service 真的少了一次 stat——漏掉第 4 点全部测试照绿。必须在 materializer.rs tests 既有 e2e 样板（`e2e_list_read_stat`，`:2295` 起，真 ZIP→物化→ArchiveMediaSource 全链）上加一个 seeded ready-cache 服务级回归：预物化后把 `mock.stat_calls` 清零，依次走 `src.stat_entry_size` + `src.read_file` 各一次 ready 命中，断言 origin stat 总数恰为 **2**（每 resolve 1 次；修复前该组合为 4）。这才是「每次 resolve 去掉第二个 HEAD」验收目标的直接证据。

**正确性边界**：identity stat 服务端变更检测（远端文件被换挡流式↔物化）依然每次 resolve 发生，不引入任何缓存陈旧窗；砍掉的只是同一次 resolve 内的第二次相同请求。新鲜度判定语义逐字节不变。

**后续优化明确不做**：秒级 TTL memo（进一步趋近 1 次）涉及跨请求状态与失效面扩张，收益递减（LAN 已近零感知），留给将来有实机延迟数据再说。

## 6. 设计决策记录（供审查修订）

1. A 项守卫比较**稳定语义键** `descriptorId(descriptor)|currentPath`，不比对象引用——FileList 内联字面量兜底（`FileList.vue:407`）使本地源引用逐渲染重建，引用比较会误杀正常回包并放大 measuredMap 清空的伤害。序号方案同样否决（同目录并发批次误杀）。
2. B 项清除放在 `invalidatePendingArchiveOnNavigate` 顶部**无条件执行**（含无在途事务的提前 return 之前）——失败的错误恰好处于无 pending 状态，这是记录措辞「不随导航清」的精确病理位置。
3. C 项采用**writeTail 串行化 + revision 判定最新请求 + confirmed 确认基准回滚 + 初载 ready 门**四件套：串行化保证完成顺序==操作顺序；revision 破 ABA（第二轮审查）；confirmed 回滚破乐观 prev 在连环失败下的传染（第三轮审查反例 2048→4096败→8192败）；ready 门破初载回填与用户写意图的竞态（第四轮审查：deferred getSetting 未决时写入挂队，防 confirmed 以默认值为基准、防迟到回填覆盖写意图）。confirmed 与显示 ref 同种子初始化并在 `loadRemoteSection` DB 回填处同步，仅成功写推进。alert 直呈不用 i18n key；不禁用控件（挂起门代替）。
4. F 项经 **trait 面四点接入**（trait 新方法带退化默认 → Materializer inherent 实现 → impl 覆盖 → service 切换），保持其余物化 mock 零适配；原签名委托不变语义。
